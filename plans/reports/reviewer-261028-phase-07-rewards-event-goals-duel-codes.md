# Review phase-07: rewards, event goals, duel codes

Daily/event claims are sound against double-claim (all checks inside tx, read-before-write ok). One real defect (duel code reuse), the rest low/medium.

## High
1. **Duel code reuse vs stale RTDB mirror** - server/duels/duel-store.ts:~71 + server/duels/duel-documents.ts:60-64. Firestore duel doc TTL 7d (docs deleted), RTDB `duels/{id}` never cleaned. 6-char codes are now reused once the Firestore doc is gone; `create` only checks Firestore. New room mirror txn: `current && rank(current) > rank(state) ? undefined : state` -> stale `finished` state under same code outranks new `waiting` -> clients (RTDB listeners) see the old finished room/winner; also stale `live/{uid}` scores persist. Old 10-char ids never collided. Fix: on create (after tx) `ref(duels/{id}).remove()` before mirror, or have mirror overwrite when `current.createdAt/startAt` differ; also remove RTDB node when doc expires. Confidence: high (~85%) that behavior occurs; likelihood low-moderate (needs ~7d old code hit; 887M space, but collision on a reused slot just needs the earlier doc deleted - random hit per create is ~N_old/887M, tiny) -> real but rare; fix cheap.
2. (Related) old ranked sessions (30d TTL) carry `duelId`; reused code lets old-session submit hit new room only if uid is host/guest of the new room (record path checks membership via recordDuelResult?) - not verified; likely harmless. Low.

## Medium
3. **Daily reward lost across midnight** - server/daily/claim-daily-reward.ts:20-26. Uses `dayKeyFor(now)` at claim; finish 23:59 VN, claim 00:01 -> 409 daily-not-done (today's doc absent), reward gone. Also streak at claim is evaluated at claim time (could be reset to 0 -> day-1 coins if streak lapsed; here it's fine as today's doc missing anyway). Fix: allow claiming yesterday's doc (day key from status), or use `dailySnap` day stored; low severity design gap. Conf 80%.
4. **Rank reward computed before tx, board still writable** - server/events/event-rewards-store.ts:97-104. Previous-week board can still change: event sessions keep `eventWeek` of start and are accepted up to 30d (create-ranked-game-session.ts:23), so late submits after week end raise scores of last week (own score is unchanged by claim since the claim reads outside tx; but a player can submit a high late run, then claim - fine; the reverse: claiming rank early then submitting a better late run gives no extra). Effect: rank/coins not stable at claim time; also the claim can be taken at 00:00 Mon while in-flight runs from Sunday are unsubmitted -> inconsistent ranks. Cheap mitigation: reject submit to event board when week != current (record-submitted-ranked-game.ts boardIds), or gate rank claim on a grace period. Conf 70%.
5. **Rank claim: coins computed outside tx from entry read outside tx** - same file :97-104. Benign for double-claim (flag inside tx) but `best` for milestones also read outside; scores only grow, so no over-claim. OK, noted only.
6. **Count query cost** - event-rewards-store.ts:46-49,66-80. GET /api/events does 2 aggregation counts every call (current + previous) + 4 doc reads; staleTime 30s, invalidated on every claim, home page also uses useClaimableEventRewards (same query key, shared). Aggregation bills 1 read per 1000 index entries: a 50k-player board = 50 reads x2 per poll per user. Fix: compute rank only for previous week when unclaimed (`rankClaimed` already known) and cache per-week rank for closed week; for current week skip rank when bestScore null (already) or use cap `.limit(1000).count()`. Conf 85%.
7. **Tie semantics**: rank = higher+1 (ties share rank). Matches leaderboard; ok. Entry docs from the new daily->weekly/all-time counting do not affect event board. ok.

## Low
8. **Weekly/all-time now include daily runs** - leaderboard-board-ids.ts:33. Daily seed is identical for everyone, so weekly/all-time top may be dominated by replaying-known-seed? Only first counted run/day per user and seed leaks only after day rolls (comment) - but `classic` still random. Acceptable; but all-time/weekly now mix incomparable runs (daily seed vs classic) - product call. Also improved-only writes: a daily run lower than existing weekly best is skipped correctly.
9. **Daily reward preview** - daily-status-store.ts:30-31: `streak.current + 1` when not done. If `lastDailyDay === today` yet not done (impossible) fine; if streak lapsed `current=0` -> +1 = day 1 correct; if alive from yesterday correct. Matches claim (streak after advance). OK. Edge: late-submitted run for older day (day < lastDailyDay) not advancing - fine.
10. **Coin write mixing** - claims use `stored.coins + coins` inside tx (reads user doc in tx: safe) while other writers use `FieldValue.increment` (inviter) and replay path: tx contention retries handle it. OK. If `userSnap` missing, `tx.set merge {coins}` creates partial user doc with no displayName/createdAt - negligible (daily done implies user exists; event entry too).
11. **Duel code UX/validation**: DUEL_ID_PATTERN (duel-types.ts:8) 10-char branch alphabet `[A-HJ-NP-Za-km-z2-9]` vs 6-char uppercase set; page.tsx normalizes only 6-length -> lowercase 6-char link redirects, lowercase 10-char old ids untouched (case-sensitive, correct). A 6-char lowercase string that happens to be valid? No: 6-char branch uppercase only, so lowercase 6-char fails pattern before redirect only if normalize returns null - redirect happens first, ok. Old 10-char ids: pattern, API routes ([id]/join, [id]) and RTDB rules ($duelId, no format check) all backward compatible. Verified.
12. **Enumeration**: 6-char waiting rooms joinable by guess, no rate-limit on `join`/`GET /api/duels/[id]` (ids 887M, rooms few) - negligible.
13. **React**: weekly-event-page `claim.isPending` disables all buttons globally (fine); `claim.mutate` per-call callbacks are dropped if component unmounts (toast not shown) - cosmetic. daily-reward-track: `setCelebrate` stores response; ok. use-event-queries `useClaimableEventRewards` counts previous rank claim as pending when `rankCoins>0` and not claimed, matches server.
14. **nextWeekStartMs** (daily-challenge-calendar.ts:37-42): `localDate` = VN midnight as UTC midnight; adds (8-weekday) days then subtracts 7h -> real UTC ms of VN Monday 00:00. Correct. isoWeekKeyFor previous-week via `now - 7d` correct incl. year boundaries.
